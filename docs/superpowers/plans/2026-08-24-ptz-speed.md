# PTZ speed dropdown — implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One dropdown in the Settings tab with three choices — איטי / בינוני / מהר — that sets how fast the camera pans, tilts and zooms.

**Architecture:** The speed lives in `CameraSettings` as a three-value string, so it persists per camera and each split-screen console keeps its own. `vmd/desktop/steering.py` stays pure maths and gains a `speed` argument instead of reading module constants; every steering path (arrow keys, mouse edge, zoom) multiplies through the same factor. The dropdown copies the existing sensitivity dropdown exactly.

**Tech stack:** Python 3.12, PySide6, pydantic (`Model`), pytest.

---

## The decisions this plan makes

| Decision | Choice | Why |
|---|---|---|
| Where it is stored | `CameraSettings.ptz_speed` | It is a property of the camera; each console has its own `settings.json` |
| Values | `"slow" \| "normal" \| "fast"` | Matches the `sensitivity` field's shape exactly |
| Default | `"normal"` | **Preserves today's behaviour byte for byte** |
| Factor | 0.5 / 1.0 / 2.0 applied to today's constants | Normal is unchanged; slow halves; fast doubles |
| Mouse-edge steering | **Now scaled too** (behaviour change) | Today it runs to ±1.0 while arrows cap at 0.5 — mouse steering is silently twice as fast. See Task 2. |
| Lens creep zoom | Scaled, but **never above `CREEP_SPEED`** | `lenses.py:55` documents that a fast zoom on a 2-second feedback loop overshoots every time |
| Labels | Hebrew | Asked for. It will be the only Hebrew in an otherwise English UI. |

**Clamping is mandatory everywhere:** ONVIF takes −1..1. `fast` doubles, so an unclamped edge value would reach 2.0 and the camera would refuse the command.

## Traps — read before writing a line

These were found by reading the zoom path end to end. Each one turns a working console into a broken one, and none of them is visible from the diff.

1. **Zero must stay exactly zero.** The zoom stop is produced arithmetically: `ZOOM_SPEED * direction` with `direction == 0` on key release (`live.py:2852`), and `Lenses.creep` chooses between moving and stopping on `if speed:` truthiness (`lenses.py:430`). Any multiplier expressed as an offset, a floor, or a `max(minimum, ...)` turns key-release into **a head that never stops zooming** — the one failure this tab exists to prevent. Multiply; never add, never floor.

2. **`Lenses.creep` throws the caller's magnitude away.** Line 431 is `self._camera.move(0.0, 0.0, _sign(speed) * CREEP_SPEED, profile=token)` — only the *sign* of `speed` survives. Scaling the value that `ZoomBar` emits, or that `PtzService.zoom_hold` passes, **changes nothing at the camera**. Only `CREEP_SPEED` itself moves that lens.

3. **There are two `0.35`s.** `CREEP_SPEED` in `vmd/ptz/lenses.py:57` (reaches the wire) and `CREEP` in `vmd/desktop/zoombar.py:79` (emitted in the signal, and does not). Scale one and not the other and the console's own readout disagrees with what the camera was sent. Both, or neither.

4. **Absolute zoom must never be scaled.** `Lenses.go_to(stream, where)` sends a *position* in 0.0–1.0 via AbsoluteMove (`onvif.py:654`), with no `<Speed>` element at all. Multiplying `where` is not "zoom slower", it is "zoom to the wrong place".

5. **`fast` already saturates.** ONVIF clamps to ±1.0 (`onvif.py:722`). `ZOOM_SPEED` 0.5 × 2.0 = exactly 1.0, so `fast` is the ceiling — a larger factor later would be indistinguishable from it. Say so in the comment rather than leaving room for a "very fast".

6. **A speed change does not reach a key already held.** `_drive` drops repeats by comparing the whole `(pan, tilt, zoom)` tuple (`live.py:2754`), and `self._zoom` is cached. This is acceptable for a Settings dropdown — the operator is not steering while the Settings tab is open — but if the speed ever becomes a live control, `apply()` must re-drive.

7. **The `+`/`−` keys and the zoom bar drive different lenses.** The keys go through `move()` with no profile, so ONVIF uses the camera's *default* profile; the bar addresses the per-picture lens. Both are scaled, and they are not the same motor.

- [ ] **Step 3a: Create `vmd/ptz/speed.py`**

The factor table lives here and not in `steering.py`, because `vmd/ptz/lenses.py` needs it too and `vmd/ptz/` must never import `vmd/desktop/` — that would point the camera layer at the GUI layer. `vmd/desktop/` already imports `vmd/ptz/`, so this direction is the existing one.

```python
"""How fast the operator asked the camera to move. One table, two readers.

`vmd/desktop/steering.py` scales the pan and the tilt with it, and
`vmd/ptz/lenses.py` scales the zoom creep with it. It lives here, in the camera
package, because the camera package may not import the desktop one.
"""

from __future__ import annotations

# Multipliers on the speeds this console already used, rather than three tables
# of absolute speeds. "normal" is 1.0, so it is arithmetically identical to what
# every install did before this choice existed: an operator who never opens the
# dropdown cannot find his camera moving differently.
#
# 2.0 is the ceiling, not a step on a ladder. ONVIF clamps at 1.0 and the zoom
# base is 0.5, so "fast" already asks for the fastest thing the protocol can
# express; a "very fast" above it would be indistinguishable at the camera.
FACTOR = {"slow": 0.5, "normal": 1.0, "fast": 2.0}


def factor(speed: str) -> float:
    """The multiplier for a chosen speed. Anything unrecognised is normal.

    Never raises. The value arrives from a settings file a person can edit by
    hand, and a KeyError here would surface inside a Qt key handler - the one
    place in this program an exception must not reach.
    """
    return FACTOR.get(speed, 1.0)


def onvif_range(value: float) -> float:
    """Clamp to the range ONVIF accepts.

    Not decoration. `fast` doubles, and the edge band already reaches 1.0 at
    full depth, so an unclamped corner would ask the camera for 2.0 - which it
    refuses outright rather than quietly capping, meaning the head does not move
    at all in exactly the gesture the operator makes when he wants it to move
    most.
    """
    return max(-1.0, min(1.0, value))
```

- [ ] **Step 3b: Rewrite `vmd/desktop/steering.py`**

Replace lines 10–47 with:

```python
from vmd.ptz.speed import factor, onvif_range

# The outer band of the picture that steers. Inside it, speed grows with depth,
# so a nudge and a fast slew are the same gesture rather than two modes.
EDGE_FRACTION = 0.14

NORMAL_SPEED = 0.5
FINE_SPEED = 0.08


def key_velocity(held: set[str], fine: bool, speed: str = "normal") -> tuple[float, float]:
    """(pan, tilt) for the arrow keys currently held.

    `held` contains any of "left", "right", "up", "down".
    """
    base = (FINE_SPEED if fine else NORMAL_SPEED) * factor(speed)
    pan = (-1 if "left" in held else 0) + (1 if "right" in held else 0)
    tilt = (-1 if "down" in held else 0) + (1 if "up" in held else 0)
    return (onvif_range(pan * base), onvif_range(tilt * base))


def edge_velocity(x: float, y: float, speed: str = "normal") -> tuple[float, float]:
    """(pan, tilt) for a pointer at fractional position (x, y) in the picture.

    (0, 0) is the top-left corner. Tilt is inverted because screen coordinates
    grow downwards and cameras do not.

    Scaled by the chosen speed, which it was not before: the band ran from 0 to
    a full 1.0 while the arrow keys capped at NORMAL_SPEED, so the same camera
    steered at two different rates depending on whether the operator used the
    mouse or the keyboard. Now both are the same speed, and the dropdown moves
    both.
    """
    x = min(max(x, 0.0), 1.0)
    y = min(max(y, 0.0), 1.0)
    base = NORMAL_SPEED * factor(speed)

    def component(position: float) -> float:
        if position < EDGE_FRACTION:
            return -(EDGE_FRACTION - position) / EDGE_FRACTION
        if position > 1.0 - EDGE_FRACTION:
            return (position - (1.0 - EDGE_FRACTION)) / EDGE_FRACTION
        return 0.0

    pan = component(x) * base
    tilt = -component(y) * base
    return (round(onvif_range(pan), 3), round(onvif_range(tilt), 3))
```

- [ ] **Step 3: Add the capped helper**

In `vmd/ptz/lenses.py`, below `CREEP_SPEED = 0.35`:

```python
from vmd.ptz.speed import factor


def creep_speed(speed: str = "normal") -> float:
    """How fast a lens creeps, for the operator's chosen speed.

    Capped at CREEP_SPEED and never above it. The comment on that constant is
    a measurement, not a taste: the zoom readback on this link takes about two
    seconds, and a creep faster than this overshoots the mark every time and
    leaves the operator hunting. So "fast" makes the pan and the tilt faster
    and leaves this exactly where it was - which is the honest answer, and
    better than a zoom that obeys the dropdown and cannot be aimed.
    """
    return min(CREEP_SPEED, CREEP_SPEED * factor(speed))
```
